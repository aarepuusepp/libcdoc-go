# CDOC 1.1 ECC Decryption Failure Analysis and Fix Guidance

## Purpose

This document summarizes the issues found in the generated `encrypted.cdoc` container compared to the working `TEST.cdoc` container. It is intended to be used as input for Cursor.AI so the Go library can be corrected to produce interoperable **Estonian CDOC 1.1** encrypted containers.

The affected implementation is in the uploaded Go archive (`libcdoc-go-archive.zip`).

---

## Executive Summary

The primary decryption failure is caused by an incorrectly encoded **`PartyUInfo`** value in the ECC recipient metadata.

In the generated `encrypted.cdoc`:
- `PublicKey` is encoded as an EC uncompressed point: `0x04 || X || Y`
- `PartyUInfo` is encoded incorrectly as: `0x00 || X || Y`

In the working `TEST.cdoc`:
- `PublicKey` is encoded as: `0x04 || X || Y`
- `PartyUInfo` is encoded as: `0x00 || 0x04 || X || Y`

Because `PartyUInfo` is one of the inputs into the ECDH/ConcatKDF key derivation process, this encoding mismatch causes a different key-encryption key (KEK) to be derived. As a result, the wrapped content-encryption key cannot be correctly unwrapped, and decryption fails.

A second major issue is that the current `ConcatKDF()` implementation does **not** appear to follow the XML Encryption 1.1 / NIST SP 800-56A ConcatKDF structure. Even if `PartyUInfo` is fixed, this KDF implementation should also be corrected to ensure interoperability.

## Issue 1 — Incorrect `PartyUInfo` Encoding

### Severity

**Critical** — highly likely to be the direct reason decryption fails.

### Observed Difference

The working reference file encodes:

- `PublicKey` = `04 || X || Y`
- `PartyUInfo` = `00 || 04 || X || Y`

The generated failing file encodes:

- `PublicKey` = `04 || X || Y`
- `PartyUInfo` = `00 || X || Y`

This means the EC point prefix byte `0x04` is missing from `PartyUInfo`.

### Why This Breaks Decryption

For ECC-based XML Encryption / CDOC 1.1 recipient processing, `PartyUInfo` is part of the key derivation context. If the sender encodes `PartyUInfo` incorrectly, the recipient will derive a different KEK than expected. That immediately breaks AES Key Wrap unwrapping of the encrypted file master key.

### Likely Root Cause in the Code

The problem is caused by the mismatch between two code paths:

#### Current behavior in `cdoc/composer.go`

1. `encodeECPublicKeyBytes()` builds only raw coordinates:
   - `X || Y`
   - no uncompressed point prefix byte `0x04`

2. `PublicKey` later gets the `0x04` prefix added separately.

3. `PartyUInfo` is built from the raw output of `encodeECPublicKeyBytes()` and prefixed only with `00`, resulting in:
   - `00 || X || Y`

### Required Fix

The same EC public key byte representation must be used consistently for:

- the XML `PublicKey`
- the `PartyUInfo` KDF input

For an uncompressed EC point this should be:

- `0x04 || X || Y`

Then `PartyUInfo` must become:

- `0x00 || 0x04 || X || Y`

### Recommended Refactoring

Replace the current raw-coordinate encoding helper with a helper that returns the full uncompressed point.

### Suggested Patch Direction

```go
func encodeECPublicKeyUncompressed(pubKey ecdsa.PublicKey) ([]byte, error) {
    xBytes := pubKey.X.Bytes()
    yBytes := pubKey.Y.Bytes()

    raw := make([]byte, 96)
    copy(raw[48-len(xBytes):48], xBytes)
    copy(raw[96-len(yBytes):], yBytes)

    return append([]byte{0x04}, raw...), nil
}
```

Then use the returned bytes for **both** XML `PublicKey` and `PartyUInfo`.

Example direction:

```go
partyUInfo, err := encodeECPublicKeyUncompressed(ephemeralPrivKey.PublicKey)
if err != nil {
    return nil, err
}

publicKeyBase64 := base64.StdEncoding.EncodeToString(partyUInfo)

recipient := RecipientRecord{
    PublicKey:  publicKeyBase64,
    PartyUInfo: "00" + hex.EncodeToString(partyUInfo),
    // ... other fields
}
```

### Additional Validation Rule

Add an internal assertion/test:

- decoded `PublicKey` length must be `97` bytes for P-384 uncompressed point
- decoded `PartyUInfo` length must be `98` bytes (`00` + 97-byte public point)
- `PartyUInfo[1:]` must equal decoded `PublicKey`

## Issue 2 — `ConcatKDF()` Implementation Does Not Match XMLENC / NIST Structure

### Severity

**Critical / High** — likely causes interoperability failures.

### Observed Problem

The current `crypto/ec.go` implementation appears to derive the KEK using a non-standard digest construction equivalent to:

```text
SHA-512(sharedSecret || AlgorithmID || PartyUInfo || PartyVInfo)
```

However, XML Encryption 1.1 ConcatKDF is based on the NIST SP 800-56A KDF pattern and requires structured input of the form:

```text
K(1) = H(counter || Z || OtherInfo)
```

where:
- `counter` is a 4-byte big-endian integer starting from `0x00000001`
- `Z` is the ECDH shared secret
- `OtherInfo` contains the context fields such as `AlgorithmID`, `PartyUInfo`, `PartyVInfo`, etc.

### Why This Is a Problem

If the KDF input structure is wrong, the sender derives the wrong KEK. That makes the AES Key Wrap operation produce a wrapped key that cannot be unwrapped by standard implementations.

### Additional Interoperability Concern

The XML metadata indicates the digest method as `sha384`, but the code reportedly uses `sha512` directly in the KDF implementation. The digest algorithm used in the actual KDF must match the declared XML Encryption metadata.

### Required Fix

Re-implement `ConcatKDF()` according to XML Encryption 1.1 / NIST SP 800-56A:

1. Select the hash function based on the XML `DigestMethod`
   - e.g. SHA-384 when the metadata says SHA-384

2. Build `OtherInfo` correctly from the XMLENC context values
   - `AlgorithmID`
   - `PartyUInfo`
   - `PartyVInfo`
   - optional `SuppPubInfo`
   - optional `SuppPrivInfo`

3. Compute output blocks using:

```text
H(counter || Z || OtherInfo)
```

4. Truncate to the required KEK size
   - for AES-256 Key Wrap: 32 bytes

### Suggested Implementation Outline

```go
func ConcatKDF(hash func() hash.Hash, z []byte, otherInfo []byte, keyDataLen int) []byte {
    hashLen := hash().Size()
    reps := (keyDataLen + hashLen - 1) / hashLen

    var result []byte
    for counter := 1; counter <= reps; counter++ {
        h := hash()

        var ctr [4]byte
        binary.BigEndian.PutUint32(ctr[:], uint32(counter))

        h.Write(ctr[:])
        h.Write(z)
        h.Write(otherInfo)

        result = append(result, h.Sum(nil)...)
    }

    return result[:keyDataLen]
}
```

The exact construction of `OtherInfo` must follow the CDOC 1.1 / XMLENC conventions expected by interoperable implementations.

### Important Action

Do **not** keep a hardcoded SHA-512 in ECC KDF if the XML metadata declares SHA-384.

## Issue 3 — Potential Digest Method / Metadata Mismatch

### Severity

**High** — can independently break interoperability.

### Observed Problem

The container metadata indicates a digest algorithm such as SHA-384, but the actual KDF code appears to use SHA-512 regardless of the metadata.

### Required Fix

Ensure that:

- the XML `DigestMethod` value is mapped to a concrete Go hash implementation
- the selected hash is used consistently in the actual KDF computation
- serialization and cryptographic behavior agree exactly

### Recommended Rule

Treat cryptographic metadata as authoritative. If the XML says SHA-384, the implementation must actually perform KDF with SHA-384.

---

## Issue 4 — `PublicKey` / `PartyUInfo` Generation Should Share One Canonical Encoder

### Severity

**Medium / High** — structural bug source.

### Observed Design Problem

The current code seems to generate `PublicKey` and `PartyUInfo` through different transformation steps, which caused them to drift apart.

### Required Fix

Introduce one canonical function for serializing an EC public key in the exact form required by CDOC/XMLENC.

Recommended invariant:

- `publicPoint := encodeECPublicKeyUncompressed(pub)`
- `PublicKey = base64(publicPoint)`
- `PartyUInfo = "00" + hex(publicPoint)`

This avoids accidental divergence.

---

## Issue 5 — Missing Regression Tests for Container Interoperability

### Severity

**High** — allowed the bug to pass unnoticed.

### Required Fix

Add automated tests that validate the generated XML recipient data before container packaging.

### Recommended Tests

#### 1. EC Public Key Serialization Test

Verify for P-384 ephemeral keys:
- encoded point length is `97` bytes
- byte `0` equals `0x04`
- X and Y are left-padded to 48 bytes each

#### 2. `PartyUInfo` Consistency Test

Verify:
- `PartyUInfo` starts with `00`
- `len(PartyUInfoBytes) == 98`
- `PartyUInfoBytes[1:] == decodedPublicKey`

#### 3. ConcatKDF Test Vector

Create a deterministic test using:
- fixed ephemeral private key
- fixed recipient public key
- fixed `AlgorithmID`, `PartyUInfo`, `PartyVInfo`
- expected KEK bytes

This should detect any future drift in KDF behavior.

#### 4. Round-Trip Interoperability Test

Generate a CDOC container with a known certificate and confirm it can be decrypted by a reference-compatible implementation.

#### 5. Reference Comparison Test

Generate a container and compare the recipient XML structure against a known-good reference for:
- `EncryptionMethod`
- `DigestMethod`
- `PublicKey`
- `PartyUInfo`
- `PartyVInfo`
- `CipherValue`

## Issue 6 — Missing or Divergent Metadata Fields

### Severity

**Low / Medium** — probably not the direct cause of decryption failure, but worth aligning.

### Observed Differences

Compared to the working `TEST.cdoc`, the generated `encrypted.cdoc` appears to differ in non-cryptographic metadata, including:

- missing `EncryptionProperty` such as `orig_file`
- different `Recipient` display/name formatting
- XML declaration/prolog differences

### Why It Matters

These differences probably do not directly cause ECC key unwrap failure, but they may:
- reduce compatibility with stricter tools
- break metadata expectations
- create confusing differences during debugging

### Required Fix

Align non-cryptographic metadata generation with the working reference behavior wherever possible.

### Recommended Actions

- add `orig_file` if required by the target ecosystem
- normalize `Recipient` formatting to the expected convention
- produce XML that is as close as possible to the reference serializer output

## Notes for the Implementer

Do not treat the working `TEST.cdoc` and failing `encrypted.cdoc` as merely cosmetic variants. The `PartyUInfo` difference is cryptographically significant.

The most likely immediate root cause of the current decryption failure is:

- **missing `0x04` EC point prefix inside `PartyUInfo`**

The most likely follow-up interoperability problem, even after fixing that, is:

- **non-standard `ConcatKDF()` implementation and/or digest mismatch**

Both must be corrected for reliable CDOC 1.1 ECC compatibility.
